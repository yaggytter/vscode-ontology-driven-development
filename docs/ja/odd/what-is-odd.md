# オントロジー駆動開発とは

**オントロジー駆動開発（Ontology-Driven Development、ODD）**は、要件定義のあと、設計に入る前にオントロジーを作り、そのオントロジーを開発の最後まで正本として使い続ける開発の進め方です。

ここでいうオントロジーは、次の2つを機械可読な形で書いたものです。

- 業務に**何が存在するか**（モノ、その性質、モノ同士の関係）
- それを**どう変えてよいか**（操作、操作の条件、副作用）

記法には [Object Ontology](../reference/object-ontology-format.md)（`*.oont.yaml`）を使います。この拡張機能と `oont` CLI で、オントロジーを作り、レビューし、検証し、開発に使います。

## なぜ設計の前にオントロジーを作るのか

要件は文章で書かれ、設計はテーブルやクラスや API で書かれます。その間で、多くの問いが誰にも確かめられないまま決まっていきます。最初にテーブルを書いた人が決めてしまうことも少なくありません。

- 「予約」と「利用」は別のものか
- 取り消した予約は削除するのか、状態が変わるだけか
- 1つの予約で複数の会議室を押さえられるか
- 誰が、いつまでなら取り消せるのか

オントロジーを作ると、こうした問いに意識して答えることになります。答えは、業務担当者も開発者も AI エージェントも読める小さなファイル1つにまとまります。設計の前に書くので、答えはデータベースの都合ではなく業務から出てきます。機械可読なので、ツールで検査でき、後の工程の成果物をオントロジーから作ったり、オントロジーと突き合わせたりできます。

## 既存の方法論との違い

| | 従来のオントロジー駆動の開発（OWL/RDF 中心） | ドメイン駆動設計（DDD） | オントロジー駆動開発 |
| --- | --- | --- | --- |
| 主な関心 | 知識の厳密な形式化と推論 | 境界づけられたコンテキストごとのモデル | コンテキストをまたぐ概念と操作の正本 |
| 記法 | OWL、RDF | コード、図、ユビキタス言語 | 軽量な YAML（Object Ontology） |
| 操作の扱い | 扱わない | 集約やドメインサービスとして設計時に決める | アクション型として設計前に書く |
| AI との関係 | 想定していない | 想定していない | エージェントのコンテキストとツール定義の源泉にする |

DDD を置き換えるものではありません。オントロジーで概念と操作を固めてから、DDD で境界づけられたコンテキストや集約を設計する、という順に組み合わせます。

## 工程

```text
要件定義 → オントロジー作成 → レビュー → 設計 → 実装 → 検証
              ↑                                      │
              └──── 要件の変更・概念の揺れの発見 ──────┘
```

| 工程 | やること | 成果物 | この拡張機能でできること |
| --- | --- | --- | --- |
| 要件定義 | 要件に ID を振って一覧にする | 要件一覧（`REQ-001` など） | オントロジーの隣に Markdown で書く |
| オントロジー作成 | 要件からオブジェクト型・リンク型・アクション型を抜き出し、各要素に実現する要件の ID を付ける | `*.oont.yaml` | 入力中に「問題」パネルに出る診断、`oont validate`、JSON Schema による補完 |
| レビュー | 業務担当者と図を見ながら、概念と操作に合意する。確認した問いと答えを残す | レビュー済みのオントロジー、確認事項の記録 | 図、Inspector の**要件**欄、**アクション**パネル |
| 設計 | オントロジーをモジュール、DB、API に割り当て、コンテキストの境界を決める | 設計ドキュメント | SPARQL による依存関係の分析、要件ごとの要素の一覧 |
| 実装 | オントロジーを根拠に実装する。AI エージェントにはオントロジーをコンテキストとして渡す | コード、テスト | `oont export summary`・`oont export tools`（拡張機能のエクスポートと同じ内容） |
| 検証 | 実装がオントロジーと合っているか確かめる。アクション型ごとにテストがあるかを見る | テスト結果 | 今は手作業 |

要件が変わったときは、コードより先にオントロジーを直します。オントロジーの差分が、そのまま変更の影響範囲の説明になります。「Booking を変更するアクションはどれか」のような影響範囲は SPARQL で調べられます。

## 要件からオントロジーを作る

要件の文から、次の順に抜き出します。

| 要件の中にあるもの | Object Ontology | 会議室予約の例 |
| --- | --- | --- |
| 業務で扱うモノ（名詞） | `objectTypes` | 会議室、予約、社員 |
| モノの性質 | `properties` | 定員、開始時刻、状態 |
| モノ同士の関係 | `linkTypes`（多重度つき） | 予約は1つの会議室を押さえる |
| 業務の操作（動詞、ユースケース） | `actionTypes`・`parameters`・`rules` | 予約する、取り消す、チェックインする |
| 業務ルール、制約 | `validations` | 時間帯が重なる予約はできない |
| 操作に伴う通知など | `sideEffects` | 解放したら予約者に通知する |
| 具体例 | `objects` | 会議室 A（定員4） |

抜き出しながら、次の問いを立てます。答えが出ないものは業務担当者に確認します。

- **同一性**：何をもって同じモノとするか（主キーは何か）。似た言葉は同じモノか、別のモノか
- **ライフサイクル**：モノは消えるのか、状態が変わるだけか。状態にはどんな値があるか
- **多重度**：関係は1対1か、1対多か、多対多か
- **権限と条件**：その操作は誰が、どんな状態のときにできるか
- **例外**：ルールを破りたくなるのはどんなときか

[ハンズオンのチュートリアル](tutorial-requirements-to-ontology.md)で、会議室予約を題材にこの手順を通して試せます。

## 原則

1. **概念を先に、実装を後に。** テーブルやクラスの都合で概念を決めません。「同じものか、別のものか」「消えるのか、状態が変わるのか」を設計の前に決めます。
2. **存在だけでなく操作まで書く。** 何をいつ、誰が、どんな条件で変えられるかを、アクション型として書きます。要件のユースケースと業務ルールの大部分はここに入ります。
3. **オントロジーはコードと同じリポジトリに置く（Ontology as Code）。** 変更はプルリクエストで行い、差分でレビューします。
4. **小さく始めて、反復で育てる。** 最初から網羅しようとしません。完成を待たずに設計へ進み、設計や実装で見つかった概念の揺れはオントロジーに戻して直します。
5. **オントロジーが下流を駆動する。** 型、スキーマ、API、テスト、AI エージェントのツールは、オントロジーから作るか、オントロジーと突き合わせて検査します。食い違ったら、正しいのはオントロジーです。
6. **人間と AI が同じオントロジーを読む。** 業務担当者との合意も、AI エージェントへの指示も、同じファイルを根拠にします。
7. **要件までたどれるようにする。** オントロジーの各要素に、どの要件から来たかを残します。

## 各工程で使う機能

| したいこと | 使うもの |
| --- | --- |
| 完成した例から始める | **ODD: サンプルオントロジーを作成...** → **会議室予約（Object Ontology）** |
| 書きながら誤りに気づく | 「問題」パネル（参照切れ、未知のフィールド、[要件の診断](../reference/object-ontology-format.md#要件の診断)） |
| 業務担当者とレビューする | 図（`Cmd+Alt+O` / `Ctrl+Alt+O`）、Inspector の**要件**欄、**アクション**パネル |
| 要件をたどる | SPARQL のサンプル **9. 要件と、それを実現する要素**、LLM 向け要約の `## Requirements` 節 |
| CI やエージェントから検証する | [`oont validate`](../reference/cli.md) |
| AI エージェントにオントロジーを渡す | `oont export summary`・`oont export tools`、または対応する **ODD: ...エクスポート** コマンド（[チュートリアル6](../ai/tutorial-6-object-ontology-ai-agents.md)） |
| 用語集や外部の知識とつなぐ | 拡張機能の Semantic Web 側の機能（OWL・RDF・SKOS のファイル、Object Ontology の Turtle エクスポート）（[オントロジー方式の選び方](../learn/choosing-ontology-style.md)） |

## 現時点の制約

- validation の `expr` は、人と AI エージェント向けの説明です。ツールは評価しません。将来テストの生成に使えるよう、式の書き方を揃えておくことをおすすめします。
- 実装がオントロジーと合っているかの検証は、今は手作業です。
- 一覧や検索のような読み取り専用の問い合わせを書く場所は、まだありません。必要なら要件一覧の側に残してください。
